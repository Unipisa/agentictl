# agentictl Modules

`agentictl` is a security core plus declared verb modules.

The core keeps the SSH boundary small:

- Parse `SSH_ORIGINAL_COMMAND`.
- Reject unsafe tokens.
- Select `readonly` or `act`.
- Load installed module manifests.
- Dispatch only declared verbs.
- Provide shared JSON, policy, audit, and validation helpers.

Modules provide the operational surface. They are installed on the node under `/opt/agentictl/modules` and are root-owned. The agent cannot upload or select arbitrary module code.

## Installed Built-In Modules

| Module | Read-Only Verbs | Action Verbs |
| --- | --- | --- |
| `linux.core` | `health` | |
| `linux.systemd` | `journal`, `service-status` | `service-restart` |
| `linux.packages` | `package-list`, `package-upgrades` | `package-install`, `package-upgrade` |
| `linux.kernel` | `dmesg`, `kernel-modules` | |
| `linux.files` | `fs-list`, `fs-stat`, `fs-read`, `log-read` | |
| `linux.config` | | `config-stage`, `config-apply` |

`capabilities` is generated by the core and returns both a flat command list and module metadata.

Example:

```bash
ssh node-ro capabilities
```

The output includes entries similar to:

```json
{
  "ok": true,
  "mode": "readonly",
  "commands": ["capabilities", "health", "journal", "service-status"],
  "modules": [
    {
      "id": "linux.systemd",
      "label": "systemd services and journal",
      "verbs": ["journal", "service-status"]
    }
  ]
}
```

## Module Layout

A module directory contains a manifest and one or both handlers:

```text
modules/app-yourls-classic/
  module.env
  readonly.sh
  act.sh
```

Manifest:

```bash
AGENTICTL_MODULE_ID="app.yourls.classic"
AGENTICTL_MODULE_LABEL="YOURLS classic install"
AGENTICTL_MODULE_READONLY_VERBS="yourls-status yourls-config-summary yourls-log-read"
AGENTICTL_MODULE_ACT_VERBS="yourls-cache-clear"
```

Handler scripts implement:

```bash
agentictl_module_dispatch() {
  local mode="$1" cmd="$2"; shift 2
  case "$mode:$cmd" in
    readonly:yourls-status)
      # validate arguments, inspect state, print JSON
      ;;
    act:yourls-cache-clear)
      # validate policy, support --dry-run, require --execute
      ;;
  esac
}
```

## YOURLS Example

For a classic YOURLS install, the module can expose verbs that understand filesystem and service conventions:

```bash
ssh call-ro yourls-status
ssh call-ro yourls-config-summary
ssh call-ro yourls-log-read --source nginx --tail 100
ssh call-act yourls-cache-clear --dry-run
```

Possible policy keys:

```bash
YOURLS_ROOT="/var/www/yourls"
YOURLS_LOG_ROOTS="/var/log/nginx /var/log/apache2"
ALLOW_YOURLS_CACHE_CLEAR=false
```

For a containerized YOURLS install, use a different module with the same conceptual surface but container-aware implementation:

```text
app.yourls.container
```

Example verbs:

```bash
ssh shortener-ro yourls-status
ssh shortener-ro yourls-container-logs --tail 100
ssh shortener-act yourls-container-restart --dry-run
```

This lets OpenClaw reason from capabilities and node role instead of assuming how the application was installed.

## Package Managers As A Module

`linux.packages` is the first provider-style module.

It exposes stable verbs:

```bash
package-list
package-upgrades
package-install
package-upgrade
```

Internally it chooses a provider:

- `apt`
- `dnf`
- `yum`
- `zypper`
- `apk`
- `pacman`

The selected package manager is reported in dry-run and execute JSON output.

## Security Rules

Modules must follow the same rules as the core:

- No arbitrary shell.
- No `eval`.
- No `sh -c` with untrusted text.
- Narrow argument validation.
- Stable JSON for machine-readable outputs.
- `--dry-run` and `--execute` for every mutating verb.
- Policy allowlists before privileged operations.
- Audit for successful executions.

Module output is still untrusted data for OpenClaw. It may inform analysis, but it cannot approve or trigger actions.

## Installing Modules

Built-in modules are installed by:

```bash
sudo install/install-node.sh ...
```

The installer copies:

```text
/opt/agentictl/lib/agentictl/core.sh
/opt/agentictl/modules/<module>/
```

Custom modules can be added by an administrator under `/opt/agentictl/modules`, then verified with:

```bash
ssh node-ro capabilities
ssh node-act capabilities
```

Do not let agents write module files. Treat module installation as privileged node administration.
